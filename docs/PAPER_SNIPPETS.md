## 1. 项目背景与问题定义（可替换/扩写版）

MedCipher Studio 面向生物医药与医疗健康等高敏感数据场景，核心难点并不在于“有没有密码算法”，而在于如何把业务语言快速、准确地映射为可落地的密码工程方案。在多中心协作、跨境科研、临床试验数据流转等真实场景中，系统常同时满足“最小权限”“审计可追溯”“数据不出域”“资源受限”“合规要求多且动态变化”等约束。传统方案设计往往需要业务、密码、合规、工程多角色多轮协作，沟通成本高、交付周期长，且方案难以复用与审计复核。

因此，我们提出 MedCipher Studio：以自然语言为入口，通过多智能体协同把“需求解析-方案设计-安全与合规审计-代码工程化-交付报告”串成一条可追踪的自动化流水线，目标是降低方案设计门槛、提升交付效率，并让输出自带证据与审计依据，便于教学评审与实际落地。

## 3.2 系统总体架构（配图 2 的图解段落模板）

图 2 展示了 MedCipher Studio 的整体分层架构。系统以 `FastAPI` 提供统一后端接口，前端以 `React (Vite)` 作为主要交互入口，并保留 `Streamlit` 作为轻量演示与内部调试入口。后端核心由 `MASOrchestrationService`（Supervisor）编排，串联 Requirement Analyst、Cryptography Architect、Security & Compliance Auditor、Code Engineer 四类智能体，形成端到端的方案生产线。

在“检索增强”层面，系统维护了一套本地结构化组件知识库（YAML 形式），共 152 个密码组件条目，按 `primitives / modes / protocols` 分层组织，并为每个组件记录参数、性能、兼容性、适用场景与参考来源。方案生成阶段会先从知识库中按安全等级、平台与场景约束检索候选集合，再将候选集的结构化描述注入到 LLM 的选择/组合提示中，从而降低幻觉与随意拼接风险。同时引入兼容性规则与启发式兜底，保证在 LLM 不可用或输出不稳定时仍可产出可审计的“最佳努力”方案。

最终交付不仅包含可运行代码（或可编译的模板）与方案说明，还会生成合规报告、漏洞扫描报告、候选方案对比与可信度评估快照，便于课堂评审与后续复核。

## 4. 多智能体协同机制（Supervisor + 4 Agents，可扩写版）

MedCipher Studio 采用 Supervisor 统一编排的多智能体流水线。与单一大模型直接输出方案不同，多智能体架构将“理解需求”“设计方案”“审计放行”“工程落地”解耦为可追踪、可回放的阶段，减少一次性生成导致的不可控风险，并让每阶段都有明确输入输出与失败处理策略。

1. Requirement Analyst 负责将自然语言需求抽取为结构化规格，输出关键约束（安全等级、平台资源、合规目标等），并显式给出歧义点、默认假设与澄清问题清单。当启用严格澄清模式时，Supervisor 会在发现必答澄清项后直接阻断流程，避免基于错误前提生成“看似合理但不满足约束”的方案。
2. Cryptography Architect 以“检索增强”的方式从组件知识库筛选候选集合，再结合 LLM 选择与组合能力生成多个候选方案变体。变体之间通过候选窗口轮转与多次尝试避免重复，从而覆盖不同安全-性能-复杂度取舍。
3. Security & Compliance Auditor 对候选方案进行漏洞扫描与合规评估，输出整体合规分、风险分、关键发现与建议修改项。若候选方案未通过审计，Supervisor 会先在候选之间切换；当所有候选均被拒绝时，会触发一次“加固（Hardening）”，例如提升密钥强度或补充后量子组件，再进入下一轮审计。
4. Code Engineer 将最终方案工程化为 Python/C/伪代码等产物，并对生成代码执行语法检查。当检测到编译/语法失败时，系统采用“安全模板回退”策略，以最小可用的方式保证交付物可被课堂复核与二次开发。

### 编排伪代码（可直接放入报告增强技术感）

```text
Supervisor.execute(requirement):
```

## 7. 知识库、规则库与轻量 RAG 设计（可扩写版）

### 7.1 组件知识库的结构化设计

与仅存放“算法名称列表”的做法不同，MedCipher Studio 将密码组件以结构化 YAML 方式维护在本地知识库中，当前共 152 个组件条目，其中 `primitives` 122 个、`modes` 16 个、`protocols` 14 个。每个组件条目不仅记录名称与类别，还包含参数范围（如 key_size/nonce_size/tag_size）、性能侧写（软件速度、硬件速度、内存、功耗）、安全属性（安全级别、最佳攻击、标准化状态）、兼容性（compatible_with/not_compatible_with）、适用场景（use_cases）与参考来源（standards/papers）。

这种结构化表达的直接收益是：系统可以在生成阶段先做“硬过滤”（例如安全级别、平台约束、兼容性约束），再将候选集的关键信息以摘要形式注入 LLM 提示，从而把大模型的自由发挥限制在可控空间内，降低幻觉与不兼容组合的概率。

### 7.2 检索与选择策略（可直接写入你们的 RAG 设计小节）

系统的候选检索并非“纯向量检索”或“纯大模型自由生成”，而是混合策略：

1. 安全等级过滤：优先检索满足目标安全等级的组件。在 AEAD 等组合场景下，对 MAC/mode 组件采用更宽松的合格标准，避免因单组件安全级别标注导致的过度过滤。
2. 场景/平台过滤：对加密类需求按平台映射到 use_case（如 IoT/mobile/server），尽量优先取适配场景的组件集合。当场景标签不足时退化为更宽松的候选集合。
3. 候选窗口轮转：将候选集合切片为固定窗口，并按 variant_index 轮转窗口位置，从而在多变体生成时扩大搜索空间，减少“所有方案看起来一样”。
4. LLM 选择与兼容性补全：LLM 返回候选索引并给出理由。当组合不完整或不满足 AEAD 结构时，系统根据兼容性元数据与内置规则补全组件（例如 ChaCha20 + Poly1305、AES + GCM/CCM）。
5. 启发式回退：当 LLM 不可用或选择失败时，启发式策略按方案类型生成“最佳努力”组件组合，并在必要时执行一次加固（提升 key_size、补充 PQC 组件等）。

### 7.3 组件条目示例（建议放 1 个到正文，增强“做了知识库”的可信度）

```yaml
name: AES
category: block_cipher
parameters:
  block_size: 128
  key_size: [128, 192, 256]
```

## 8. 鲁棒性与回退（Fallback）机制（可扩写版）

真实环境里，输入常包含歧义、缺项与冲突约束。同时大模型输出也可能出现不完整组合、格式错误或“看似合理但不满足约束”的情况。为此系统将鲁棒性设计拆为三类能力：

1. 输入侧的澄清与假设显式化：对缺失的关键工程约束（如内存预算、时延目标、主合规标准）生成澄清问题。在严格模式下阻断执行，避免基于错误假设进入后续阶段。
2. 生成侧的约束注入与结构化输出：组件选择与架构生成均要求结构化输出，降低“长文本难解析”带来的工程风险。同时通过候选集注入与兼容性规则约束，减少不兼容组合。
3. 执行侧的多级回退：当 LLM 解析/生成不可用时，启发式路径仍可产出可审计方案。当代码生成导致语法/编译失败时，采用安全模板回退保证交付物可复核。

（可选扩写点）可以在这里补一张“失败类型 -> 回退策略”表：

| 失败类型 | 触发信号 | 回退策略 | 代价 |
|---|---|---|---|
| 需求缺关键约束 | required 澄清项存在 | 严格模式直接停；非严格写入假设并继续 | 交付延迟/假设风险 |
| LLM 不可用 | provider 异常 | 启发式解析/启发式方案生成 | 方案质量下降 |
| 审计拒绝 | risk/compliance 未达标 | 切换候选；必要时 hardening 一次 | 额外审计轮次 |
| 代码语法失败 | compile/check fail | 退回安全模板并给出原因摘要 | 代码精细度下降 |

BuildCipher · 攻击 Pipeline 人类版说明

这套系统里的“攻击”不是盲打，
而是一条可解释、可回放、可收口的验证链路

它的核心思想不是“让模型随便攻击”，而是先让系统理解当前目标服务和风险重点，再规划本轮攻击动作， 然后在受控环境里执行有限探测，最后把结果交给漏洞评估、专家判断、修补与反思模块，形成闭环。

它在解决什么

不是证明模型会说攻击术语，而是证明系统能围绕一个实际部署出来的目标服务，做出有节制、有依据的验证动作。

它为什么重要

只有经过攻击验证和漏洞裁决，前面的方案生成和代码实现才不只是“看起来合理”，而是进入了可检验状态。

它当前做到哪

现在已经具备真实的 LLM 决策式攻击规划，以及本地受控环境中的探测执行和结果沉淀能力。

它还没做到哪

当前仍是演示级、本地受控执行，不是面对真实公网目标的隔离攻击基础设施。

先用一张图看完整流程

准备

部署本地服务

把方案实现包装成一个可调用的本地服务，形成后续攻击验证的目标对象。

理解

读取风险与上下文

系统先看已有证据、审计结论、历史问题和目标服务画像。

规划

制定攻击动作

攻击决策层决定本轮该继续打、换打法、直接评估，还是先停下来。

治理

做预算与审批

系统先检查攻击族、探测次数、运行时和预算是否符合约束。

执行

发起有限探测

对本地服务做健康检查和加密接口探测，记录延迟、流量和响应表现。

沉淀

收集工件

把轨迹、度量、发现项、运行日志沉淀成后续可以回看的结构化工件。

裁决

评估漏洞

漏洞评估层判断严重度、影响范围、可利用性和整改优先级。

分流

决定下一步

专家判断层决定是继续补充攻击、进入修补，还是直接观察收口。

闭环

修补并反思

对问题做修补与回归验证，并把经验回灌给下一轮方案生成与审计。

2

逐阶段解释：系统到底是怎么“攻击”的

阶段一：准备一个可被验证的目标服务

从“算法描述”走向“可测试对象”

当前阶段在做什么

系统会把方案实现包装成一个本地服务，让它具备可调用、可观察、可记录的运行形态，而不是只停留在伪代码或静态代码文本。

为什么这么做

如果没有一个真实运行的目标对象，后续所谓“攻击”只能停留在纸面推测，无法验证服务在实际请求下会表现成什么样。

系统如何执行

系统在本地创建一个受控服务环境，为它生成运行信息、日志位置和后续探测所需的基础工件。

结果意味着什么

这一步完成后，攻击阶段面对的就不再是“概念方案”，而是一个能被请求、能被观测的服务目标。

阶段二：攻击决策层先决定“打什么、怎么打、还要不要打”

真实 LLM 决策层

当前阶段在做什么

系统会先根据目标服务画像、当前风险重点、上一轮发现和当前任务模式，决定本轮攻击动作。

为什么这么做

攻击不应该是机械重复，而应该根据“当前证据够不够”“补丁后还需不需要回归”“继续攻击是否还有价值”来调整策略。

系统如何执行

攻击决策层会输出本轮动作，例如继续执行、改成回归验证、直接转漏洞评估，或者在没有新增价值时停止攻击。

结果意味着什么

这说明系统并不是固定打一套脚本，而是会根据上下文做选择，这也是“攻击 agent 具有决策能力”的核心体现。

阶段三：攻击前先做治理与预算控制

防止无边界执行

当前阶段在做什么

在真正执行之前，系统会先检查本轮攻击任务是否符合白名单、预算和运行约束。

为什么这么做

这是为了保证攻击阶段始终处于可解释、可控、可回放的范围内，避免模型输出一个动作就直接被执行。

系统如何执行

系统会审查本轮攻击类别、任务数量、预计探测次数、超时时间以及当前执行后端是否允许进入执行。

结果意味着什么

只有通过审批的攻击动作才会被下发；如果不通过，系统会留下“为什么被阻断”的记录，而不是悄悄失败。

阶段四：在本地服务上执行有限探测

当前实际攻击执行面

当前阶段在做什么

系统会对本地服务先做可用性确认，再围绕加密接口做若干次受控探测，观察它的响应、流量、延迟和运行表现。

为什么这么做

这一步的重点不是追求“破坏性攻击”，而是先建立一个真实的执行基底：服务是否正常、接口表现如何、是否出现异常风险信号。

系统如何执行

系统会向本地服务发送一组受控样本请求，同时记录发送字节、返回字节、响应时间和运行中观测到的资源指标。

结果意味着什么

攻击阶段不再只是“模型口头分析风险”，而是已经能够基于真实调用结果形成结构化攻击结果。

阶段五：把攻击过程沉淀成可回看的工件

可追溯、可解释、可展示

当前阶段在做什么

系统会保存攻击轨迹、性能度量、发现项摘要和服务运行日志，让后续评估与展示都基于同一批证据对象。

为什么这么做

如果没有工件沉淀，后面的漏洞评估和专家判断就会重新回到“只看文字描述”的状态，难以支撑企业交付和回放分析。

系统如何执行

系统把每轮探测结果整理成时间序列、指标摘要、发现项摘要和支撑工件，供后续模块读取，而不是把大量原始细节直接硬塞进上下文。

结果意味着什么

这使得“攻击结果”成为一个稳定对象，既能喂给漏洞评估，也能给前端做图表、给 replay 做回看、给报告做证据引用。

阶段六：漏洞评估层给出结构化裁决

不是停留在“打完就结束”

当前阶段在做什么

系统会根据攻击结果判断问题的严重程度、可利用性、影响范围和整改优先级。

为什么这么做

攻击本身不是目的，目的是把“观察到的现象”转成“可以进入决策和整改的安全判断”。

系统如何执行

系统综合攻击工件、原始风险背景和当前服务状态，形成一份结构化漏洞裁决，作为后续分流的依据。

结果意味着什么

从这一刻开始，系统已经不只是在“做攻击实验”，而是在做“安全验证决策”。

阶段七：专家判断层决定是继续、修补还是收口

闭环的分流器

当前阶段在做什么

系统会在漏洞评估之后做一次更高层的判断：是继续补充攻击、进入修补流程，还是先把当前结果作为观察结论收口。

为什么这么做

因为不是每次发现都需要立刻修补，也不是每次都值得继续攻击。系统需要一个“安全与工程共同视角”的判断层。

系统如何执行

系统会结合漏洞严重度、残余风险、后续建议和当前预算，决定下一步进入哪条分支。

结果意味着什么

这一步决定了攻击阶段是不是会继续，也决定了整个系统能否形成真正的多轮闭环，而不是打一轮就结束。

阶段八：修补、回归与反思，让下一轮更聪明

从“发现问题”走向“自我优化”

当前阶段在做什么

若需要整改，系统会生成修补建议、执行补丁后的回归验证，并沉淀反思结论，用于下一轮方案生成和审计。

为什么这么做

真正有价值的 agent 系统，不是只会指出问题，而是能把问题带回生成与审计环节，逐步减少同类失误。

系统如何执行

系统会把当前漏洞、补丁方向、回归结果和反思摘要压缩成下一轮可复用的记忆卡片和优化提示。

结果意味着什么

攻击 pipeline 不再只是“验证模块”，而开始成为整个系统自净化和持续改进的一部分。

3

这条攻击链路现在的真实含义

它已经说明了什么

  • 系统已经不是只会“说攻击思路”，而是能围绕一个实际运行的目标对象做出决策和执行。
  • 攻击阶段已经具备“决策、审批、执行、沉淀、评估、分流、回灌”七个关键环节。
  • 攻击结果已经能进入前端可视化、回放追踪、专家判断和最终交付，而不是一次性日志。
  • 这条链路已经具备多 agent 闭环的雏形，尤其适合用来展示后端技术深度。

它还不应该被误写成什么

  • 不应写成“已具备真实公网渗透能力”。
  • 不应写成“已完成生产级隔离沙盒”。
  • 不应写成“已形成无限轮次自我攻击系统”。
  • 更准确的说法是：当前已完成真实 LLM 决策下的演示级攻击验证闭环。

适用于答辩展示、项目介绍、企业汇报与非技术背景读者理解当前攻击 pipeline 的工作方式。

# 引用驱动交付（Citation-Driven Delivery）设计

最后更新：2026-03-24
状态：draft
适用范围：`src/cipher_genius/api/report_service.py`、`src/cipher_genius/api/schemas.py`、`src/cipher_genius/reporting/`、`frontend/src/features/mas/ReportsView.jsx`、导出链路

## 1. 目标

引用驱动交付要解决的不是“页面上多显示几条来源”，而是让关键交付结论变成：

- 有依据
- 能回指
- 可复盘
- 可导出
- 可答辩

本文回答 5 个问题：

1. 为什么“只有建议，没有来源”不够
2. 什么内容必须带引用
3. claim/source 结构应该怎么设计
4. 为什么引用不能只停留在 UI 层
5. 适合按什么顺序落地

## 2. 当前现状

当前项目已经具备一些“接近证据化”的基础：

- 可信度评分
- 证据覆盖率
- 组件证据视图
- 中文优先交付模板
- 报告聚合与导出链路

但目前还没有形成统一的引用结构。常见现状是：

- 系统能说“建议这样做”
- 也能给出一些来源汇总
- 但关键结论和来源之间还不是稳定的一对一或一对多映射

这会导致交付更像“系统总结”，而不是“带依据的企业交付结论”。

## 3. 为什么当前状态还不够

如果报告只给建议、不明确来源，企业侧通常会继续追问：

- 这条建议依据是什么
- 是来自标准、案例还是组件边界
- 哪些是规则判断，哪些是模型推断
- 这条结论能不能进入正式评审材料

如果这些问题答不清，系统输出很容易被看作：

- 一个写得比较好的 AI 总结

而不是：

- 一个可审阅、可追责、可复盘的交付物

## 4. 什么内容必须带引用

不是所有文本都要强行带引用，但下面几类内容强烈建议必须支持引用：

### 4.1 审计结论

例如：

- 为什么拒绝
- 为什么通过
- 哪些标准不满足
- 哪些风险项仍未关闭

### 4.2 整改建议

例如：

- 为什么要补密钥轮换策略
- 为什么要换成更稳妥的候选组合
- 为什么某类部署方式不推荐

### 4.3 最终上线建议

例如：

- 是否建议进入上线评审
- 还需要哪些人工检查
- 哪些限制下才可投产

### 4.4 关键组件判断

例如：

- 为什么推荐某个模式或算法
- 为什么不建议某个组合
- 组件的能力边界或兼容限制是什么

## 5. 推荐的数据结构

### 5.1 核心思想

建议把“交付结论”拆成两层：

- `claim`
  - 系统要表达的结论
- `sources`
  - 支撑这条结论的来源集合

也就是说，不再只输出大段自然语言，而是输出“有结构的结论对象”。

### 5.2 推荐 claim schema

```json
{
  "claim_id": "audit-remediation-001",
  "claim_type": "recommendation",
  "title": "建议补齐密钥轮换策略",
  "summary": "当前方案在密钥轮换策略上仍不完整，建议补充轮换周期、触发条件与审计留痕要求。",
  "decision_rule": "audit.non_compliant.key_rotation",
  "confidence": 0.86,
  "sources": [
    {
      "doc_id": "std-cn-health-001",
      "chunk_id": "std-cn-health-001#5.4",
      "title": "某建筑工程数据交付规范",
      "section": "5.4 密钥轮换周期要求",
      "snippet": "......",
      "score": 0.93,
      "source_type": "standard"
    }
  ]
}
```

### 5.3 推荐 source schema

每条来源至少建议包含：

- `doc_id`
- `chunk_id`
- `title`
- `section`
- `snippet`
- `score`
- `source_type`
- `source_path` 或外部引用定位信息

如果来源是案例，还建议补：

- `case_id`
- `accepted_option`
- `audit_findings`

## 6. 为什么引用不能只停留在 UI 层

这是这条主线最容易被做歪的地方。

如果引用只在页面上额外展示一下，会有 4 个问题：

### 6.1 导出物丢失依据

很多企业场景真正流转的是：

- Markdown 报告
- HTML 报告
- PDF
- 审批材料

如果引用只在前端临时展示，导出之后依据就没了。

### 6.2 API 层没有统一结构

如果后端不先定义 claim/source schema，前端就会倾向于拼装展示逻辑，最终每个页面各写一套。

### 6.3 无法做稳定回归

如果引用只是 UI 细节，很难写出这类回归：

- 关键报告里是否真的出现引用块
- 关键建议是否真的带来源
- 中文交付导出里是否保留引用说明

### 6.4 无法支撑答辩

答辩里最有说服力的是：

- “这是系统的结构化结论”
- “这是支撑这条结论的来源”

而不是：

- “页面上好像能点开几条来源”

## 7. 和检索、Case Memory 的关系

这条主线不应独立看待，它和另外两条能力一起构成闭环：

### 7.1 检索负责提供 evidence

检索层负责：

- 把标准、案例、组件知识卡召回出来
- 形成 `evidence_pack`

### 7.2 Case Memory 负责提供项目上下文

Case Memory 负责：

- 补充本项目的历史整改、已确认约束和被拒方案

### 7.3 Citation Delivery 负责把依据绑定到结论

交付层负责：

- 把 evidence pack 和项目上下文绑定到最终 claim 上
- 输出给前端和导出链路

所以它不是“单独多做一页引用展示”，而是检索、记忆、交付三者之间的最后一公里。

## 8. 在本项目中的推荐落地顺序

### 阶段 1：先定义 schema

优先做：

- `claim`
- `source`
- `evidence_pack`

即使前端暂时还没完全展示，后端也要先把结构定下来。

### 阶段 2：先覆盖最关键的交付块

优先把以下位置改成带引用：

- 审计拒绝原因
- 整改建议
- 上线建议
- 关键组件结论

不要一开始就要求所有文本都带引用。

### 阶段 3：进入导出链

让以下导出保留引用块：

- HTML
- Markdown
- PDF 输入内容

### 阶段 4：补回归测试

验证：

- 报告中必须出现引用结构
- 关键建议必须能看到中文标题和来源摘要
- 导出物不能丢失引用块

## 9. 为什么它比“把来源列表挂在报告后面”更强

把来源统一挂在报告最后面，也能看，但仍然存在一个问题：

- 不知道哪条来源对应哪条结论

Citation-Driven Delivery 更强的地方在于：

- 引用和结论是绑定的
- 可以知道“这条结论的依据是什么”
- 可以把规则命中、证据来源、置信度放进同一个对象

这比“最后附一个参考资料列表”强得多。

## 10. 用户使用方式会怎么变

从用户表面上看，还是：

- 输入需求
- 查看结果
- 导出报告

但结果的性质会变化：

- 以前：看到的是建议
- 以后：看到的是“带依据的建议”

这对企业场景尤其重要，因为很多交付不是为了“看起来聪明”，而是为了“能够拿去评审”。

## 11. 推荐验证方式

落地后至少应验证：

- `MASResponse` 或相关报告对象里，关键结论是否带 claim/source 结构
- `ReportsView.jsx` 是否能稳定渲染引用块
- HTML / Markdown / PDF 导出是否保留引用信息
- 中文标题和中文建议是否仍然保留
- 关键引用是否能回到原始来源片段，而不是只剩标题
